Per-query cost semantics for later policy comparisons
A recorded per-query generation cost includes its original attempts, failures,
retries and observed provider prompt-cache discounts. It can be used to estimate
what the selected query generation historically cost at configured rates.
Call it 'recorded historical API cost', not fully cold generation cost.
Reusing a completed local generation artifact makes no new paid call. Its
historical cost/duration remains attached for fair mode comparisons. Lookup and
local I/O overhead are not estimated by the historical API duration.
Same-language translation is an exact identity bypass: known zero API calls,
tokens, cost and API duration. Encoding/search costs remain unpriced.
Generation is shared across eight retrievers and multiple target settings.
Do not sum repeated per_query rows or report summaries to estimate a bill.
A policy's stand-alone per-encoder cost can be reported separately. If evaluating
several policies or encoders together, count their union of needed generation
keys once. Training/tuning costs and all-language oracle availability must be
separated from the cost of selected test-query generation.
The pricing-only sensitivity of charging every observed input token at the
standard uncached rate would be USD 0.41158510 translation and USD 0.89611140 HyDE.
These are counterfactual prices on the recorded token traces, not measured cold
runs or a latency forecast. They do not include compute or rerunning tuning.

Timing definitions and limits
Generation_seconds sums perf_counter durations around each non-streaming HTTP
call and JSON decoding. Successful-call duration excludes local schema parsing;
failed-call duration includes the failing parse/validation path. It excludes
Slurm waiting, inter-job/manual retry gaps, request-cache lookup, model loading,
embedding, retrieval, and serialization of the finished artifact. Summed call
seconds across concurrently executing jobs are not elapsed campaign duration.
Query_encoding_seconds_amortized is the original embedding artifact build wall
time divided by its input row count. Its timer starts after encoder construction
and includes batching, token/truncation audit work, normalization and embedding/
metadata writes and flush. The exact same value is assigned to every query in a
report, and all 264 report values match their embedding manifests. It is not an
individually measured query latency; model download/loading are excluded.
Retrieval_seconds_amortized is measured search/fusion wall time divided by the
actual query batch size. All saved values match their timings.parquet sources.
It includes exact NumPy matrix scoring and document aggregation, and excludes
index loading and result serialization. Runtime device=cuda describes the
embedding configuration; DenseIndex retrieval itself uses NumPy CPU arrays.
All selected runtime configurations use embedding batch size 32, query batch
size 32 and corpus block size 16,384. GPU model/slice and comparable hardware
service rates are not supplied by these embedding/report metadata fields.
API durations, amortized encoding, and amortized search should be reported as
separate measurements. Their sum is an offline component estimate, not measured
online end-to-end response latency. Cache reuse must not erase historical work
or be presented as the measured cost of a new uncached generation.
GPU/CPU/memory/storage, corpus preparation/embedding, model loading/downloads,
Slurm resource allocations/queues, networking and question-dataset creation
have no price accounting here. Their cost is unknown, not zero.
